# 03: 性能运行与判定闭环

**What to build:** 让测试人员完成真实性能采集、阅读报告，并追加重分析而不改变原始判定。

**Blocked by:** None (can start immediately)

**Status:** resolved

**规格依据：** TestDock 首个可交付版本收口规格；用户故事 7、10、11、17、18、19。

## Acceptance criteria

- [x] 通过页面选择或登记固定性能场景及资源，完成真实采集；报告中的采集时长、指标及来源可追溯。
- [x] 性能前置条件不满足时明确说明原因，不把设备在线等同于性能就绪。
- [x] 缺失指标展示为空值与原因，不写零；样本或可比条件不足时如实未判定，保持既有三态门禁规则。
- [x] 对历史运行追加重分析，确认原始判定和原始证据未被改写；不可比资源档案按现有规则处理。
- [x] 在线报告和适用图表可读，证据可访问；独立性能场景不声称执行过 UI 业务动作。
- [x] 复用性能与判定既有行为测试及有效真机证据；补测缺口，记录实际运行与判定身份。

## 执行与证据边界

- 本票负责完整业务路径及其暴露的范围内缺陷，优先复用已有实现、测试入口和有效证据，不增加未经约定的架构或依赖。
- 每次有意义的修改后检查实际受影响行为。证据注明提交与工作区变化、环境和操作；涉及未提交代码时不能只以 HEAD 标识版本。
- 只在隔离数据和经授权的资源上执行。设备、可信套件、桌面会话等是环境前提，缺失时记录影响与解除条件；不伪造通过，不阻塞其他独立工作。
- 同设备验收需要错峰，共享设备不构成新的工单依赖。其他工单尚未完成不妨碍复核本票自身证据。
- 本组工单的发布不代表执行授权；后续实施遵守规格的数据、设备、依赖与发布边界。不得覆盖其他工作的修改，不修改或关闭父规格。
